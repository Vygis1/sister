# Nintendo 64

Where this stands, what the target is, and the order the rest happens in. As
with the PlayStation, each step can be tested on its own, and none waits on a
later one.

## The rule on sources

This core is written here. It is not a port.

The one serious open N64 core, MiSTer's (Robert Peip, GPL-3.0), was used for
one thing: to measure whether an N64 can fit this chip at all. Its code is not
read for implementation, so that the licence of this project stays the owner's
choice. These are the references instead, all with permissive licences:

| Reference | Licence | Used for |
|---|---|---|
| [ares](https://github.com/ares-emulator/ares) | ISC | behaviour of every part, when the documents are unclear |
| [n64brew wiki](https://n64brew.dev) | documentation | registers, memory map, pipeline facts |
| [CEN64](https://github.com/n64dev/cen64) | BSD-3 | second opinion on the CPU and RSP |
| [libdragon](https://github.com/DragonMinded/libdragon) | Unlicense | an open IPL3 and a toolchain for test programs |
| [krom's N64 tests](https://github.com/PeterLemon/N64) | Unlicense | CPU, COP1, RSP, RDP and RDRAM test ROMs |
| [nemu64-test](https://github.com/thelemmy/nemu64-test) | MIT | CPU, COP0, TLB, exceptions, RSP |

## Will it fit

Measured on 2026-10-02 by synthesising MiSTer's complete core for this part
(out of context, the Altera memories swapped for inferred ones):

| | used | of the XC7A100T |
|---|---|---|
| LUTs | 45.5k | 72% |
| block RAM | 68.5 tiles | 51% |
| DSP | 63 | 26% |

| Block | LUTs |
|---|---|
| CPU | 13.3k, of which FPU 3.6k and COP0 with the TLB 4.0k |
| RSP | 10.5k |
| RDP | 12.3k |
| VI | 3.1k |
| PI, SI, PIF, AI | about 3.5k |

So an N64 fits, with roughly the margin the PlayStation has. The shell adds
about 6 to 7k LUTs. That is the budget for this core: **about 50k LUTs for
everything N64.**

Timing at the console's clocks was the hard part there, and will be here:
- 93.75 MHz for the CPU missed by 2.3 ns at synthesis. The worst paths are the
  TLB lookup in the load/store address path, and an unpipelined 64-bit
  multiply.
- 62.5 MHz for the RDP missed by 4.8 ns, on a few paths from the render mode
  into the combiner and blender.

## The target

**A test ROM's PASS on the dashboard.** krom's CPU tests draw their results
with the CPU into a framebuffer, as text. That needs:
- the CPU's integer instructions;
- RDRAM;
- the cartridge, and PI DMA from it;
- a boot that needs no PIF ROM;
- the VI scanning a framebuffer out to the stream.

It does not need the RSP or the RDP. It is the smallest thing that is visibly
an N64, and every later part is tested the same way: its own test ROM, its own
screen of results.

## What is needed from outside

**Nothing copyrighted.**
- **Boot:** the PIF ROM is not needed. The boot is done here the way
  emulators do it: the CIC seed in the registers, the cartridge's boot code
  copied into SP DMEM, a jump to 0xA4000040.
- **Games:** bring your own, as with every other machine here.
- **Test ROMs:** built from the repositories above. libdragon's IPL3 is open,
  so the test ROMs need no Nintendo boot code either.

## Where things live

| DDR3 | |
|---|---|
| 0 MB | RDRAM, 8 MB (the Expansion Pak's size; games that check for 4 MB see 4) |
| 8 MB | RDRAM's ninth bits, 1 MB, a bit per byte (coverage and Z precision) |
| 16 MB | the cartridge, up to 64 MB |
| 80 MB | saves: EEPROM, SRAM, FlashRAM, Controller Pak |
| 96 MB | the frame capture area |

| Block RAM | |
|---|---|
| CPU | 16 kB instruction cache, 8 kB data cache, the TLB |
| RSP | 4 kB IMEM, 4 kB DMEM |
| RDP | 4 kB TMEM, line buffers |

## Where it stands (2026-10-02)

**Milestone 1 is reached: krom's CPU tests pass on the board.** The real FPGA
runs the ADD, DMULT and nested-TLB-miss exception tests to all-PASS screens,
read straight out of the board's RDRAM (`/api/n64/frame`).

- **`rtl/vr4300.v`:** the CPU, a five-stage pipeline, 6.8k LUTs. It meets
  62.5 MHz at synthesis. In simulation it matches the Python model instruction
  for instruction and leaves the same screen on every integer and exception
  test (58 ROMs: `tools/n64rtltests.py`).
- **`rtl/n64_top.v`:** the CPU and a memory adapter (each port keeps one line;
  no caches yet), plus:
  - RDRAM and the cartridge in DDR3;
  - our boot ROM (`tools/n64bootrom.py`);
  - SP memory;
  - the MI's interrupts and the VI's timing.
- **The image:** 18.5k LUTs (29%) and 34 block RAMs at 50 MHz, slack 1.0 ns.
- **The model (`tools/n64model.py`)** passes every integer and exception test
  in krom's set. Still to do:
  - the FPU;
  - the PI's DMA alignment quirks;
  - the tests that wait 33 million cycles for a timer.

Two bugs a CPU-only bench could not show, found by the whole-system bench
(`sim/tb_n64_top.v`):
- **The PC's fill lost a line's first word** when DDR3 was slow to take the
  line before.
- **An abandoned fetch answered a newer one.** The CPU drops the fetch behind
  a taken branch's delay slot without waiting for it. The adapter now matches
  each answer to the address it was read for.

## The order

1. **The CPU, integer** (`vr4300.v`). MIPS III, 64-bit, big-endian, as the
   console runs it. A Python model and a generated self-checking
   sweep, as the R3000 had (`tools/vr4300test.py`). Then nemu64-test's CPU
   set.
2. **The system:** RDRAM in DDR3 behind the caches, the MI (interrupts),
   the PI (cartridge DMA), SP DMEM/IMEM as plain memory, the boot without a
   PIF ROM.
3. **The VI** onto the existing frame stream. **The first milestone**: a test
   ROM's results on the page.
4. **COP0 in full:** the TLB, exceptions, Count/Compare. nemu64-test's TLB and
   exception sets.
5. **COP1**, the FPU. krom's CP1 tests.
6. **SI and PIF** (pads, EEPROM), and **AI** onto the existing audio ring.
7. **The RSP**: scalar, then the vector unit. krom's RSPTest.
8. **The RDP**: fill and copy, then 1-cycle, 2-cycle, textures, Z. krom's
   RDPTest. Then games.

## Clocks

Everything N64 runs from one clock to start with. The CPU will run below the
real 93.75 MHz, as the PlayStation's ran off its own clock. The console's
time base (VI timing, Count, the audio rate) is counted against real time,
not against that clock, so a slower CPU makes games slower and never wrong.
Splitting the CPU onto a faster clock is a later, measured step.
