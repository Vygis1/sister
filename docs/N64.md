# Nintendo 64

How the N64 core is built and how it is checked. Super Mario 64, Mario Kart 64 and Super Smash
Bros. run on the board; other games are untested.

## The rule on sources

This core is written here. It is not a port.

MiSTer's N64 core (Robert Peip, GPL-3.0) was synthesised once for this part, to measure whether
an N64 fits. Its code is not used as a source. These references are, all with permissive
licences:

| Reference | Licence | Used for |
|---|---|---|
| [ares](https://github.com/ares-emulator/ares) | ISC | behaviour of every part, where the documents are unclear |
| [n64brew wiki](https://n64brew.dev) | documentation | registers, memory map, pipeline facts |
| [CEN64](https://github.com/n64dev/cen64) | BSD-3 | second opinion on the CPU and RSP |
| [libdragon](https://github.com/DragonMinded/libdragon) | Unlicense | an open IPL3 and a toolchain for test programs |
| [krom's N64 tests](https://github.com/PeterLemon/N64) | Unlicense | CPU, COP1, RSP, RDP and RDRAM test ROMs |
| [nemu64-test](https://github.com/thelemmy/nemu64-test) | MIT | CPU, COP0, TLB, exceptions, RSP |
| parallel-RDP (Themaister) | MIT | the RDP model `tools/n64/n64rdp.py` and its blender tables |

## What is needed from outside

Only the game. The PIF ROM is not needed: our own boot ROM (`rtl/n64_boot_rom.v`, built by
`tools/n64/n64bootrom.py`) sits where the PIF ROM is, puts the CIC seed and the RDRAM size in
place, copies the cartridge's boot code into SP DMEM and jumps to it, as emulators do.

## Memory

| DDR3 | |
|---|---|
| 0 MB | RDRAM, 8 MB (the boot ROM reports 8 MB, the Expansion Pak's size) |
| 16 MB | the cartridge |

| Block RAM | |
|---|---|
| CPU | 16 kB instruction cache, 8 kB data cache |
| RSP | 4 kB IMEM, 4 kB DMEM |
| RDP | 4 kB TMEM, line buffers |

RDRAM's ninth bits are not stored; reads of them return 3.

## Clock

The image runs at 62.5 MHz (`tools/core.sh n64`: 1000 MHz / 16), the RCP's own clock. The CPU
runs on the same clock, below the real VR4300's 93.75 MHz. The VI's interrupt, which games keep
time by, is locked to the HDMI frame: the picture runs at 25.125 MHz, 59.821 Hz, against a real
NTSC N64's 59.826 Hz.

## The CPU — `rtl/vr4300.v`, `rtl/vr4300_fpu.v`

A VR4300: MIPS III, 64-bit, big-endian. Its behaviour is `tools/n64/n64model.py`'s, which
follows ares instruction for instruction, including the chip's odd corners.

- **Pipeline:** five stages (F, D, E, M, W). Results forward from M and W into E, except a
  load's: a load and its use cost two clocks.
- **COP0 and the TLB:** 32 entries compared at once. Each port keeps the last page it
  translated (a micro-TLB, as the chip has). A data access to another page is replayed while the
  full lookup runs from a registered address; a fetch waits one clock. KSEG0 never pays for it.
- **The FPU:** IEEE single and double in all four rounding modes, with the chip's own limits
  (subnormals and quiet NaNs trap as unimplemented unless FS flushes them). Its registers are
  written when the instruction leaves E, the commit point.
- **Caches** (`rtl/n64_top.v`): 16 kB instruction and 8 kB data, direct-mapped, as on the
  chip. The data cache writes through a small buffer. Reads wait for the buffer to empty, so no
  read overtakes a store.

## The rest of the system — `rtl/n64_top.v`

PI DMA between the cartridge and RDRAM with ares's alignment rules; the MI's interrupts; SP
memory; the SI and PIF (`rtl/n64_pif.v`: pads and the cartridge's EEPROM); the AI, whose
samples go to HDMI audio at 44.1 kHz.

## The RSP — `rtl/n64_rsp.v`

The scalar unit, its COP0 (the SP's DMA and status), and the vector unit (COP2). Its behaviour
is `tools/n64/n64rsp.py`'s, which follows ares operation for operation. A vector register is
sixteen byte lanes of LUT RAM, so a load can write one byte of one register.

## The RDP — `rtl/n64_rdp2.v` and `rtl/n64_rdp_*.v`

The RDP does every mode the model (`tools/n64/n64rdp.py`, from parallel-RDP) does, checked
against it pixel for pixel in simulation:

- fill, copy, one-cycle and two-cycle modes; textures in every format TMEM holds, with the loads,
  perspective correction, and the colour combiner and blender;
- **YUV textures:** the load splits each texel pair (U, V to TMEM's low half, Y0, Y1 to the
  high); the sampler filters chroma and luma apart (`rtl/n64_rdp_texp.v`);
- **the convert stage:** with BILERP off, any texel goes through SET_CONVERT's K0-K3;
  **convert_one** (two-cycle `G_TC_FILTCONV`) filters cycle 1's texel with cycle 0's as its
  factors;
- **the pipelined TEXEL1:** a one-cycle combiner that reads TEXEL1 gets the next pixel's
  TEXEL0, sampled in a second slot as two-cycle mode does;
- **noise** (`rtl/n64_rdp_noise.v`): the combiner's NOISE, the noise dithers and alpha compare
  against noise, seeded as the model seeds it;
- **LOAD_TLUT** from 8- and 32-bit images, an interlaced scissor's dither, a 4-bit colour image.

The registers are ares's. The command walk gathers a whole command and runs it before the next is
read.

## The picture — `rtl/n64_vid.v`

The VI's framebuffer is read out of RDRAM a line at a time (16- or 32-bit) into a four-line ring
and sent to HDMI at 640 x 480. On the way it goes through the filters the real VI has:
anti-aliasing (a pixel's coverage is its alpha bit, since the ninth bits are not stored), dedither, the divot filter, and gamma, each as the game
asks or switched by the menu's settings. Then it is scaled (replicated, smoothed, or
edge-directed) and scanlines are added if asked for.

## Tests

| Gate | What |
|---|---|
| `tools/n64/n64cputests.py` | krom's CPU tests through the Python model |
| `tools/n64/n64rtltests.py` | krom's CPU, exception and CP1 tests through the RTL CPU (`sim/tb_vr4300.v`), trace and screen against the model; `--rom` runs our own TLB test (`tools/n64/n64tlbtest.py`) |
| `sim/tb_vr4300_fpu.v` | the FPU against the model, random and edge-case operations |
| `sim/tb_n64_top.v` | the whole system in simulation |
| `tools/n64/n64rsptests.py` | krom's RSP tests through `rtl/n64_rsp.v` against the model (`sim/tb_n64_rsp.v`) |
| `tools/n64/n64rdptests.py` | krom's RDP tests through the model, against screenshots from real hardware |
| `tools/n64/n64rdprtl.py` | krom's RDP tests through the RTL (`sim/tb_n64_rdp.v`), line for line against the model |
| `tools/n64/rdpmodes.py` | the RDP modes krom's tests leave out, on 16, 32, 8 and 4-bit colour images |
| `sim/tb_n64_vid.v` | the video filters, gated by `tools/vidref.py` |
| `tools/n64/systest.py` | n64-systemtest on the board, its output read back and judged against ares |

On the board, `tools/n64/rdpcapture.py` takes one frame's RDP work off a debug image and replays
it through the model and the RTL side by side.
